* Deletes leave a tombstone (state row with `deleted = 1`, new seq). A later upsert of the same key turns it live again; an edit followed by a delete shows only the delete. Removed child rows (a voucher that lost lines) get their own tombstones, so a device that missed the sequence still learns of them.

* Scope: `src/main/snapshot/retention.ts` (stub replaced) and two additions to Phase 31's `build.ts`, made because the quota rule cannot be enforced from outside: `build(kind, {maxBytes})` (refuse before upload) and an optional `store.listObjects` check that verifies an upload before the manifest row is inserted (also exports `objectsComplete`, `snapshotCursorId`). * Quota design (decision, flagged): a hard cap instead of an estimate. The new snapshot is built and sized in memory first; it is uploaded only if `stored + new <= budget`. So at rest and at every upload the stored bytes are within the budget, which is stricter than the spec peak rule (2 x full + sum(deltas) <= budget). For a full rebuild: try to keep old full + deltas until the new full is verified; if that does not fit, drop the deltas (they are superseded by the new full anyway; devices still catch up through the postbox) and try again; if two fulls do not fit, report `over_budget` and keep the stored full (never delete the only full to make room). Budget = `snapshot_mb` x 1,000,000 bytes x `quota_headroom_ratio` (1 MB as 10^6 bytes is the smaller reading, `assumed`).
* Rules (SYNC_SPEC section 8): rebuild when there is no full, the full is older than 7 days, deltas since it reach 14 (decision, flagged: `>= 14` so that there are never more than 14, the spec says "exceed"), or delta bytes exceed 0.5 x the full; deltas not sooner than 60 min after the newest snapshot (forced rebuilds ignore the interval). Gates: flag `cloud_copy` off, plan `snapshot_mb` 0 or null (basic plan), missing license or company: nothing is read, built or uploaded.
* Prune: after a successful full, every row with a lower `seq` goes (old full and all earlier deltas), manifest row first, objects second, so a device never reads a row whose objects are gone. Orphan objects (no manifest row) are removed at the start of each run. A manifest row with missing or short objects triggers a repair: the delta cursor is reset (so no change is ever skipped), a full is forced, and the broken rows are deleted only after the new full exists (this keeps `seq` from being reused; found by the test, the first version deleted first).
* Cursor safety: whenever deltas are removed without a verified new full (quota fallback, repair) `resetCursor` is called, and the builder then builds a full next time instead of a delta that would skip the removed changes.
* Assumed / not done: `quota_headroom_ratio` is applied as a multiplier on the budget; the plan's `snapshot_mb` has no other consumer. Not done: scheduling (when `runOnce` runs: after sync cycles, daily), the flag and plan values coming from the bootstrap (`index.ts` exposes neither yet, same state as the `entries` flags), the Supabase Storage / `snapshots` implementation of `RetentionStore` (list, remove, binary upload), the `snapshot_refresh` request handler, any UI. Deleting a license's snapshots when the flag turns off is not done (the storage policy denies writes then; old objects stay until a manual cleanup).
